# ido-approve-review（审批智能审查 Skill）

本 Skill 对付款审批、合同审批或采购审批实例进行智能审查，自动识别审批类型，按对应标准生成建议卡。

---

## 审批类型识别

根据 `approval_code` 判断审批类型：

| 审批类型 | approval_code | API 接口 | 标准文件 |
|---------|---|---------|---------|
| 付款审批 | `2C701485-AF89-4FB3-AA63-EFEDA4A0BD14` | `/data/payment/{instance_code}` | `IDO_SPACE_付款审批Agent执行标准_v1.2.md` |
| 合同审批 | 9个合同模板之一（非上述付款/采购 code） | `/data/contract/{instance_code}` | `IDO_SPACE_合同审批Agent执行标准_v1.2.md` |
| 采购审批 | `F753B844-865B-4B3D-B44A-544F3178F8F1` | `/data/buy/{instance_code}` | `IDO_SPACE_采购审批Agent执行标准_v1.2.md` |

## 执行流程

### 1. 获取审批实例基本信息

调用飞书 MCP 工具获取审批实例详情：

```
feishu_approval_get_instance(instance_code: "审批实例ID")
```

获取关键信息：
- `approval_code`: 审批定义 Code（用于判断审批类型）
- `instance_code`: 审批实例 Code
- `status`: 审批实例状态
- `form`: 表单数据

### 2. 按类型查询审批详情

根据步骤1的 `approval_code` 确定类型，调用对应 API：

```bash
# 付款审批
curl -s "http://192.168.100.1:27298/hetang-payment-apply/data/payment/{instance_code}"

# 合同审批
curl -s "http://192.168.100.1:27298/hetang-payment-apply/data/contract/{instance_code}"

# 采购审批
curl -s "http://192.168.100.1:27298/hetang-payment-apply/data/buy/{instance_code}"
```

### 3. 查询关联数据

根据返回的关联编码查询补充数据：

```bash
# 关联合同（付款 → 合同）
curl -s "http://192.168.100.1:27298/hetang-payment-apply/data/contract/{contract_instance_code}"

# 关联采购（付款/合同 → 采购）
curl -s "http://192.168.100.1:27298/hetang-payment-apply/data/buy/{buy_instance_code}"

# 关联项目（如有项目编码）
curl -s "http://192.168.100.1:27298/hetang-payment-apply/data/project/{project_code}"
```

**采购审批专属**：查询参考数据表进行价格和供应商比对：

```
# 用 grep 在同目录 CSV 文件中查询
# 1. 物料均价速查表.csv — 按货号或物料名称匹配，获取历史均价、价差
# 2. 供应商主表.csv — 按供应商名称匹配，获取合格供应商库状态、历史合作次数
# 3. 物料价格历史表.csv — 价格偏离时逐笔回溯排查原因
```

### 4. 按对应标准执行审查

读取对应的标准文件：

| 审批类型 | 标准文件 | 判断体系 |
|---------|---------|---------|
| 付款审批 | `IDO_SPACE_付款审批Agent执行标准_v1.2.md` | 五项判断（真实性/合规性/必要性/价值性/承受性） |
| 合同审批 | `IDO_SPACE_合同审批Agent执行标准_v1.2.md` | 七项判断（+场景归因/风险性/履约性） |
| 采购审批 | `IDO_SPACE_采购审批Agent执行标准_v1.2.md` | 五项判断（真实性/合规性/必要性/价值性/承受性） |

三种类型的判断体系不同，但共享本文件中的通用规则（见下文）。

### 5. 生成建议卡

按对应标准文件中的建议卡模板生成。建议卡结构因类型略有差异，但均包含：

```
## {类型}审批建议卡：{流水号}

### 建议动作：{通过/条件通过/不通过/驳回补材料/暂缓/升级特批/升级确认}
### 风险等级：{低/中/中高/高}
### 建议信心：{高/中/低}——{信心来源说明}

### 主判定
{最核心问题的一句话说明}

### 关键证据 / 异常点
| 证据点 | 内容 | 影响的判断项 |
|-|-|-|
| ... | ... | ... |

### {N项}判断摘要
真实性：{结论}｜{关键描述}
合规性：{结论}｜{关键描述}
...

### 条件明细（仅条件通过时）
| # | 条件内容 | 责任人 | 截止时间 | 逾期处理 |
|-|-|-|-|-|

### AI 建议方案
{具体建议}

### 需补充 / 确认
| 缺口 | 补充人 | 优先级 |
|-|-|-|
```

### 6. 写入审批备注

调用飞书 MCP 工具将 **AI 建议方案**写入审批备注，同时 @ 审批任务负责人和提交人。

**步骤 A：获取用户姓名**

从步骤1获取的审批实例中提取：
- **提交人 open_id**：`data.instance.initiator` 字段
- **当前审批任务负责人 open_id**：`data.instance.task_list` 中状态为 PENDING 的任务的 `user_id` 字段

```
feishu_get_user_name(
  open_ids: ["提交人open_id", "审批人open_id"]
)
```

**步骤 B：发送评论并 @ 相关人**

**重要：content 参数格式要求**
- content 必须是 JSON 字符串，包含 `text` 字段，不能是纯文本
- 正确格式：`'{"text": "评论内容"}'`
- 文本中不能包含未转义的双引号，需用中文引号或单引号替代
- @ 提及**必须集中在文本开头**，不要穿插在正文中

```
feishu_approval_comment(
  instance_id: "审批实例ID",
  content: '{"text": "@审批人姓名 @提交人姓名 AI 建议方案内容"}',
  at_info_list: [
    { user_id: "审批人open_id", name: "审批人姓名", offset: "0" },
    { user_id: "提交人open_id", name: "提交人姓名", offset: "审批人姓名长度+1" }
  ]
)
```

**offset 计算规则**：从 `@` 符号开始计算，`@` 占 1 个字符。第一个 @ 的 offset 为 0。

**注意**：如果审批实例状态为 REJECTED（已结束），飞书 API 可能不允许追加评论。此时应跳过备注写入，仅上传飞书文档。

### 7. 上传飞书文档并链接

将完整建议卡上传为飞书文档，并把链接追加到备注。

```
# 使用 lark-doc skill 创建飞书文档
# 获取文档链接后追加到备注
feishu_approval_comment(
  instance_id: "审批实例ID",
  content: '{"text": "完整审查报告见飞书文档：https://..."}'
)
```

### 8. 设置文档权限

```
feishu_update_public_setting(
  token: "文档 token（从创建文档返回的 URL 中提取）",
  file_type: "docx",
  link_share_entity: "tenant_readable"
)
```

## 共享规则（三种审批类型通用）

### 核心原则

| 原则 | 说明 |
|-|-|
| **判断可追溯** | 每个结论必须附带信息来源或标注「待确认」 |
| **量化优于定性** | 凡涉及金额大小、价格高低、风险等级，必须有阈值标准或参照基准 |
| **条件可关闭** | 「条件通过」的条件必须包含四要素：内容 + 责任人 + 截止时间 + 逾期处理 |
| **证据对应金额** | 附件描述必须逐项列出、对应金额、区分凭证类型、标注风险 |
| **不自证其无** | 不能断言「不需要某物」，只能说「未发现要求」或「待确认」 |
| **证据集中管理** | 同一证据点可以影响多个判断，先集中列出再由各判断分别解释影响 |
| **主判定优先** | 金额不符、节点不符、红线、基础材料缺失等核心问题，应先处理 |
| **人工确认优先** | 审批评论中特定岗位人员（风控、法务、财务）的确认声明，可信度高于 OCR 或附件自动解析结果；OCR 结果与人工确认冲突时，以人工确认为准 |
| **首审穷尽** | 首次审查必须对全部判断项（付款5项/合同7项/采购5项）逐一检查，一次性列出所有问题；不得分批披露条件，不得为了减少单次输出而保留问题 |
| **人数据必关联项目** | 凡涉及人体生物数据采集、检测、分析（如蛋白组学、基因组学、代谢组学、临床样本检测等）的支出，无论是否收费，所属项目必须为具体项目编号，不得为「其他」；无项目关联的人数据支出 → 合规性不通过 |
| **资质链上不重复** | 同一审批链（采购→合同→付款）中，前序审批已验证的供应商资质、主体材料，后续审批不再重复要求。供应商已在合格库内或前序审批已确认资质的，营业执照/经营资质免于提供 |

### 禁止表述

| 禁止表述 | 替代表述 |
|---------|---------|
| 「不需要合同」 | 「截至审批时点，未查询到同类付款需合同的先例，**建议法务确认**」 |
| 「金额较小/较大」 | 「按公司阈值标准属『XX』级别（¥X ∈ XX范围）」 |
| 「价格合理/不合理」 | 「价格较历史均价偏离 X%」或「首次采购，无参照基准，建议确认比价」 |
| 「供应商可靠」 | 「合格供应商库内供应商（覆盖N种物料类别）」或「库外供应商，历史合作N次」 |
| 「风险可控」 | 「风险可通过以下条件控制：…（列具体条件）」 |
| 「提请关注」 | 「条件通过——条件：… 责任人：… 截止：… 逾期：…」 |

### 综合建议动作类型

| 建议动作 | 适用条件 |
|---------|---------|
| **通过** | 所有判断项支撑充分，无红线，风险低 |
| **条件通过** | 价值成立但存在可控风险，必须附加可关闭的条件 |
| **驳回补材料** | 缺少关键材料，无法形成可靠判断 |
| **暂缓** | 当前不适合，未来满足条件后可重新判断 |
| **不通过** | 事实不成立、触碰红线、价值明显不成立 |
| **升级特批/升级确认** | 规则或目标冲突较大，需要人承担判断 |

### 「条件通过」的强制规范

每项条件必须包含四要素：

| 要素 | 说明 | 正确示例 | 错误示例 |
|-|-|-|-|
| 条件内容 | 具体要完成什么 | 「补充伦理审查费正式收据并上传本审批单」 | 「完善附件」 |
| 责任人 | 指定到岗位或姓名 | 「市场运营中心/刘鸿飞」 | 「相关人员」 |
| 截止时间 | 具体天数或日期 | 「14 个工作日」 | 「尽快」 |
| 逾期处理 | 未完成怎么办 | 「逾期未补充则对应金额从项目预算冻结」 | （缺失） |

### 建议信心标准

建议信心衡量 AI 对当前建议动作的把握，不是判断项的机械加总。

| 场景 | 建议动作 | 建议信心 |
|-|-|-|
| 全部判断项支撑充分，信息完整 | 通过 | 高 |
| 核心判断通过，部分项轻微偏离或首次出现 | 通过/条件通过 | 中高 |
| 总金额一致但关键信息缺失，或部分偏离 30%+ | 条件通过 | 中 |
| 供应商为新供应商，信息不充分 | 条件通过/升级确认 | 中低 |

信心表达使用「高 / 中高 / 中 / 中低 / 低」，并附信心来源说明。

### 复查行为规范

当审批实例已有历史 AI 审查记录（可通过 comment_list 中 bot 发送的评论识别），Agent 处于**复查模式**：

**复查模式规则**：
1. **仅验证前置条件**：只检查上一轮列出的条件是否已满足，满足则放行
2. **禁止新增非红线条件**：不得在复查时提出首次审查未列出的新条件，除非属于以下情形：
   - 触碰合规或法律红线（如主体异常、黑名单、虚假材料）
   - 申请人提交的新材料暴露了首次审查时不可见的新问题
3. **新增条件必须声明**：若确需新增条件，必须在建议卡中明确说明"本条件为复查新增——首次审查时因 [原因] 未能发现"
4. **禁止条件升级**：首次审查已判定的问题级别不得在复查时升级（如将「建议确认」升级为「条件通过」的条件），除非发现新证据
5. **条件无法满足的处理**：当申请人反馈某项条件确实无法满足（如营业执照无法提供、特定资质客观上不具备等），且提供了合理解释时：
   - 判断该材料的必要等级：红线材料（如无证经营）→ 不可豁免；非红线材料（如辅助证明材料）→ 可接受的合理解释
   - 接受合理说明后，该条件不再阻碍通过，在建议卡中标注「条件 [X] 经申请人说明 [原因] 后豁免」
   - 禁止对同一事项反复要求补充——若申请人已明确表示无法提供且理由成立，不得在新一轮审查中再次列为条件
   - **税号替代营业执照**：若合同/发票/收款方信息中已包含对方税号（统一社会信用代码），执行以下查证流程，通过后营业执照不再作为必须材料：
     1. **格式校验**：税号为 18 位字符（数字+大写字母），前 2 位为登记管理机关代码，第 9 位为校验码。不符合格式的直接标注「税号格式异常」
     2. **公开查证**：用 WebSearch 搜索「[公司名称] [税号]」，如搜索结果中出现国家企业信用信息公示系统（gsxt.gov.cn）或天眼查/企查查等页面且匹配企业名称与税号一致，即视为查证通过
     3. **标注格式**：「对方税号 [税号] 已通过公开渠道核验（[企业名称]），营业执照免于提供，查证结果见 [搜索来源]」
6. **操作级决策不前置**：框架协议/开口合同中逐次发生的操作选择（如是否保价运输、单次发货方式、保险购买等），由现场负责人按实际情况决定即可，**不得作为合同签署的前置条件**。Agent 无权要求特定级别人员（如 GM）确认此类操作决策，也不得将申请人的合理决策分工（如「由山东负责人选择」）判定为不满足条件。

**复查模式识别**：审批 comment_list 中存在 bot 发送的评论（comment 内容包含"AI建议方案"或"审查报告见飞书文档"）时，自动进入复查模式。

### 附件描述规范

禁止笼统表述，必须逐项列出：

```
| # | 文件名 | 对应金额 | 凭证类型 | 风险评估 |
|-|-|-|-|-|
| 1 | XX缴费单.pdf | ¥X | 正式XX通知 | 低 |
| 2 | 微信截图.jpg | ¥Y | 非正式截图 | 中——¥Y占总额Z%，缺正式凭证 |
```

**凭证类型可信度**：审批评论中人工确认（风控/法务/财务） > 正式合同/发票 > 银行回单 > 验收单 > 截图/微信记录 > 单方说明 > OCR/附件自动解析

凭证不一致时，优先使用约束力更强的凭证，不一致处必须标注，禁止自行推测金额。

**OCR 与人工确认冲突处理**：当 OCR 提取的附件内容（如合同名称、金额、日期等）与审批评论中特定岗位人员（风控、法务、财务）的确认声明不一致时，**以人工确认为准**，并在审查结论中标注"经人工确认（[姓名]/[岗位]，[日期]），[事项] 已核实无异常"，不再将 OCR 误差列为条件或异常点。

### 确认人员清单

审批评论中出现以下人员的确认声明时，视为该领域的权威结论，Agent 应直接采信，不得以 OCR 或附件解析结果质疑：

| 姓名 | 岗位 | 确认范围 | 备注 |
|------|------|---------|------|
| 曲少萌 | 风控 | 合同真实性、公司名称、签章有效性等合同相关事项 | |

**使用规则**：
- 评论中匹配到清单内人员时，先确认该评论确为确认性声明（非纯 @提及或简短测试消息）
- 确认声明涉及范围内的事项时，直接采信，在结论中标注"经 [姓名]（[岗位]）确认，[事项] 已核实"
- 清单外人员（即使岗位看似相关）的评论不自动视为权威确认，需结合评论内容和上下文判断
- 新增确认人员时，更新本清单

### 金额大小标准化（承受性通用）

| 级别 | 绝对值范围 | 典型业务含义 |
|-|-|-|
| 极小 | < ¥10,000 | 无需特别关注承受性 |
| 小 | ¥10,000 - ¥50,000 | 月度预算内通常可覆盖 |
| 中 | ¥50,000 - ¥200,000 | 需确认当月计划 |
| 大 | ¥200,000 - ¥500,000 | 需负责人确认 |
| 重大 | > ¥500,000 | 需升级管理层审批 |

### Agent 边界与人工交接

**必须移交人工判断的情形**：

| 情形 | 移交对象 |
|-|-|
| 规则冲突且无明确例外处理机制 | 法务 / 财务 / 管理层 |
| 价格偏离 > 50% 且无合理解释 | 采购 / 财务 |
| 触碰合规红线 | 法务 / 合规 |
| 现金流极度紧张 | 财务负责人 |
| 采购金额 > ¥500,000 | 管理层 |
| 供应商未在公司准入名单 | 采购部门 |

**移交格式**：

```
⚠️ 人工判断移交：
事由：[什么事需要人决定]
AI 判断范围：[AI 能判断的部分]
需要人决定的部分：[AI 无法判断的部分]
可选方案：[A / B / C，含各自影响]
建议倾向：[AI 的推荐，附带理由]
```
